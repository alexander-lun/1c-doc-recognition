# Распознавание документов поставщиков

Демонстрационное расширение 1С:Предприятия 8.3 (режим совместимости 8.3.24), которое создает черновик «Поступления товаров» по документу поставщика:

- **электронный УПД** (XML в формате ФНС) — из файла или автоматически из входящих Диадока; реквизиты читаются из XML напрямую;
- **PDF или скан** счета/УПД/накладной — реквизиты извлекает локальная языковая модель (Ollama).

В обоих случаях 1С проверяет реквизиты и сопоставляет данные со справочниками по одним и тем же правилам.

Расширение для конфигурации [«Склад: обмен с маркетплейсом»](https://github.com/alexander-lun/1c-warehouse-exchange).

```
Диадок (GetDocuments, GetEntityContent) ─┐
XML УПД (формат ФНС 5.03 / 5.01) ────────┴──► разбор XML ───────────────────────┐
                                                                                 ├─► проверки в 1С ──► черновик поступления
PDF / скан ──► сервис извлечения текста ──► LLM (JSON по схеме) ────────────────┘   ИНН, суммы,       + журнал распознавания
               pdfplumber / tesseract        Ollama, format=schema                   сопоставление
```

**Стек:** 1С:Предприятие 8.3 (расширение конфигурации, режим совместимости 8.3.24), ЭДО, Контур.Диадок API, XML УПД в формате ФНС (5.03, 5.01), HTTP-сервисы, JSON, регламентные задания, Ollama (LLM), OCR (tesseract, OpenCV), Python (FastAPI, pytest), BSL Language Server, GitHub Actions.

## Что делает

- **Извлечение текста.** PDF с текстовым слоем читается напрямую. Сканы распознаются tesseract; перед этим с изображения удаляются линии таблицы (морфология OpenCV) — без этого tesseract терял строки товаров.
- **Структурированный ответ модели.** Запрос к Ollama `/api/chat` с параметром `format` — JSON-схемой реквизитов, поэтому ответ всегда разбирается. Модель по умолчанию `qwen2.5-coder:7b`, работает на CPU ноутбука.
- **Проверки в 1С** — модели не доверяем:
  - ИНН продавца по контрольным цифрам (10 и 12 знаков);
  - количество × цена = сумма по каждой строке; если не сходится, но по всем строкам количество × цена дает итог документа — суммы строк пересчитываются;
  - сумма строк = итог документа; если модель приняла за итог строку «в том числе НДС» (итог равен НДС 20% или 10% от суммы строк) — итог исправляется;
  - дата распознана.
- **Сопоставление.** Контрагент — по ИНН (новый создается, если ИНН корректен). Номенклатура — по точному наименованию, иначе — самая длинная позиция справочника, наименование которой входит в наименование поставщика («Кабель ВВГнг 3х2,5 (бухта 100 м)» → «Кабель ВВГнг 3х2,5»).
- **Черновик, а не проведенный документ.** Документ создается непроведенным, с флагом «Требует проверки» и списком замечаний, если что-то не сошлось. Проводит его человек.
- **Журнал распознавания** — регистр сведений: файл, способ извлечения, модель, длительность, замечания, сырой ответ модели.

## Электронные УПД и Диадок

- **Разбор XML УПД** (`рд_УПДФорматаФНС`). Файл распознается по содержимому (`<?xml`) или расширению. Поддерживаются форматы 5.03 (КНД 1115131: `НомерДок`, `ДатаДок`) и 5.01 (КНД 1115125: `НомерСчФ`, `ДатаСчФ`); продавец — организация (`СвЮЛУч`), ИП (`СвИП` с ФИО) или иностранная организация. Строки — `СведТов`: наименование, единица, количество, стоимость с НДС, код товара из `ДопСведТов/КодТов`. Кодировку (обычно windows-1251) берет из заголовка XML платформа.
- **Сопоставление по коду товара.** Если код товара поставщика совпадает с артикулом номенклатуры, строка сопоставляется точно, без поиска по наименованию.
- **Загрузка из Диадока** (`рд_Диадок`). Входящие УПД читаются постранично методом `GET /V3/GetDocuments` (`filterCategory=UniversalTransferDocument.Inbound`, `afterIndexKey`), содержимое — `GET /V4/GetEntityContent`. Каждый документ проходит тот же путь, что и загруженный файл.
  - Уже загруженные документы (по `EntityId`) хранятся в регистре `рд_ДокументыЭДО` и повторно не создаются.
  - Отметка «загружено по» (`IndexKey`) сдвигается только до первого документа с ошибкой — он попадет в следующую загрузку, а успешные после него будут пропущены как уже загруженные.
  - Запуск: регламентное задание «Загрузка входящих УПД из Диадока» или `POST /hs/docs/diadoc/pull`.
  - Авторизация — `Authorization: Bearer <токен>`. Токен выдает Контур.ID (OAuth 2.0); получение и обновление токена в расширение не входит, он задается константой.

## Расширение

| Объект | |
|---|---|
| Документ `ПоступлениеТоваров` (заимствован) | + контрагент, входящие номер и дата, сумма, «требует проверки», замечания; в табличной части — наименование поставщика, цена, сумма |
| Справочник `рд_Контрагенты` | ИНН индексирован |
| Регистр сведений `рд_ЖурналРаспознавания` | |
| Константы `рд_АдресСервисаИзвлеченияТекста`, `рд_АдресСервисаLLM`, `рд_МодельLLM` | пустые — значения для локального стенда |
| Общий модуль `рд_РаспознаваниеДокументов` | распознавание, проверки, создание черновика |
| Общий модуль `рд_УПДФорматаФНС` | разбор XML УПД |
| Общий модуль `рд_Диадок` | клиент API Диадока, загрузка входящих |
| Регистр сведений `рд_ДокументыЭДО` | загруженные документы ЭДО: идентификатор, сообщение, поступление |
| Константы `рд_АдресДиадок`, `рд_ТокенДиадок`, `рд_ЯщикДиадок`, `рд_ДиадокЗагруженоПо` | подключение к Диадоку и отметка загрузки |
| Регламентное задание `рд_ЗагрузкаИзДиадок` | по умолчанию выключено |
| Общий модуль `НастройкиОбменаВызовСервера` (заимствован) | `&Вместо("УстановитьНастройки")`: настройки `рд_` задаются тем же механизмом, что и настройки конфигурации |
| HTTP-сервис `рд_РаспознаваниеДокументов` (`/hs/docs`) | `POST /recognize`, `POST /diadoc/pull`, `GET /log` |

Расширение работает **без безопасного режима**: ему нужны HTTP-запросы к сервису извлечения текста и к модели.

## API

Ключ — тот же, что у API склада, в заголовке `X-Api-Key`.

```bash
curl -H 'X-Api-Key: my-api-key' --data-binary @upd.pdf \
  'http://127.0.0.1:8081/warehouse/hs/docs/recognize?filename=upd.pdf'
```

```json
{
  "success": true,
  "needs_review": true,
  "notes": ["Строка 3: товар \"Изолента ПВХ синяя 19 мм\" не сопоставлен с номенклатурой"],
  "extraction": "pdf-text",
  "duration_ms": 61234,
  "data": {"number": "СЧ-0087", "date": "2026-10-03", "seller": {"inn": "5001987653", "...": "..."}, "total": 6975, "items": ["..."]},
  "document": {"number": "00000000051", "posted": false, "incoming_number": "СЧ-0087", "supplier": "ООО \"ТД Монтаж\"", "...": "..."}
}
```

`201` — черновик создан (возможно, с замечаниями), `422` — документ создать не удалось (нет текста, ошибка модели, XML не является УПД), `401` — нет ключа.

Электронный УПД передается так же, `extraction` в ответе — `xml-fns`, модель не вызывается:

```bash
curl -H 'X-Api-Key: my-api-key' --data-binary @ON_NSCHFDOPPR.xml \
  'http://127.0.0.1:8081/warehouse/hs/docs/recognize?filename=ON_NSCHFDOPPR.xml'
```

Загрузка входящих из Диадока:

```bash
curl -X POST -H 'X-Api-Key: my-api-key' http://127.0.0.1:8081/warehouse/hs/docs/diadoc/pull
```

```json
{"success": true, "loaded": 2, "skipped": 0, "documents": [{"number": "00000000060", "incoming_number": "1601", "...": "..."}], "errors": []}
```

## Запуск

Нужны: база с конфигурацией «Склад: обмен с маркетплейсом», [Ollama](https://ollama.com) с моделью, tesseract с русским языком (`tesseract-langpack-rus` / `tesseract-ocr-rus`), Python 3.11+.

```bash
ollama pull qwen2.5-coder:7b

# расширение в базу
scripts/build.sh ../1c-warehouse-exchange/build/ib

# сервис извлечения текста
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn doc_text:app --app-dir service --port 8091
```

Публикация — как в основном проекте; в `default.vrd` нужен атрибут `publishExtensionsByDefault="true"`, иначе HTTP-сервисы расширений не публикуются. После загрузки новой версии расширения публикацию стоит перезапустить — иначе сеансы веб-сервера могут держать старые метаданные.

Другие адреса и модель задаются константами расширения — в интерфейсе или тем же параметром запуска, что и настройки основной конфигурации:

```bash
1cv8c ENTERPRISE /F <база> /C "НастроитьОбмен;рд_АдресСервисаLLM=http://gpu-host:11434;рд_МодельLLM=qwen2.5:14b"
1cv8c ENTERPRISE /F <база> /C "НастроитьОбмен;рд_АдресДиадок=https://diadoc-api.kontur.ru;рд_ЯщикДиадок=<boxId>;рд_ТокенДиадок=<токен>"
```

Пустые константы Диадока означают локальный стенд с заглушкой API (`http://127.0.0.1:8092`, ящик `test-box`).

## Тесты

```bash
PYTHON=.venv/bin/python scripts/test.sh -m service   # сервис извлечения текста, без 1С
PYTHON=.venv/bin/python scripts/test.sh -m "not llm" # без модели: API, электронные УПД, Диадок
PYTHON=.venv/bin/python scripts/test.sh              # всё, включая распознавание через 1С и модель
```

`scripts/test.sh` поднимает сервис извлечения текста и заглушку API Диадока ([tests/diadoc_mock.py](tests/diadoc_mock.py), порт 8092): она проверяет токен и ящик, отдает список документов страницами по 2 и содержимое документов.

Тестовые документы — вымышленные, генерируются `tests/make_samples.py` (fpdf2): УПД, счет, ТОРГ-12, ИП с 12-значным ИНН, УПД с неверным ИНН, скан без текстового слоя. Ожидаемые значения — в `tests/samples/expected.json`. Электронные УПД генерирует `tests/make_xml_samples.py`: формат 5.03 от организации с кодами товаров и 5.01 от ИП с ценой, которая не делится нацело (`expected_xml.json`).

`test_edo.py`: разбор XML обоих форматов без модели, сопоставление по коду товара, ошибочный и «чужой» XML; загрузка из Диадока через несколько страниц, повторный запуск, повторно присланный документ, документ с ошибкой (отметка загрузки не сдвигается, документ запрашивается снова).

CI (GitHub Actions): анализ кода расширения BSL Language Server, ruff, тесты сервиса извлечения текста с tesseract. Тесты с 1С и моделью запускаются локально.

На ноутбуке (Ryzen 7 5700U, CPU) распознавание документа занимает около минуты; модель выгружается из памяти после прогона тестов.

## Ограничения

- Таблицы на несколько страниц и сложные формы (с переносами в ячейках) не проверялись.
- Сопоставление номенклатуры простое; для реального использования нужен справочник соответствий наименований поставщика.
- Формы — автоматические; удобнее была бы форма проверки черновика рядом с исходным файлом.
- Клиент Диадока проверен на заглушке, повторяющей документированные методы API, а не на реальном ящике. Подпись документа и титул покупателя не формируются — только загрузка в учет.
- Из XML читаются реквизиты, нужные для поступления; корректировочные УПД (УКД) не поддерживаются.
